九次改版：一个雅思刷词工具的四十二天

发表于2026-09-16|更新于2026-10-31|项目
|总字数:1.4k|阅读时长:4分钟|浏览量:

先给结论：一个背单词工具的核心不是题目，是记忆；而记忆的正确性不由「写入」决定，由「删除」和「换账号」决定。

写入错了用户会立刻发现，删除错了不会——那个词会在某天从另一台设备上原地复活。这个项目 42 天 55 次提交，绝大部分在跟这类「不会报错的错误」较劲。

一、第二天就把界面重写了

09-17 的提交信息很直白：rewrite UI/UX, per-word sync and data-safety fixes。

第一天搭出来的东西能跑，但同步是按整章一个 JSON blob 存的。两台设备一起答题，后写的那份会把先写的整章覆盖——这不是 bug，是数据模型选错了。在 blob 上打补丁只会让它更贵，所以重写。

同一天跑了真实端到端，抓到两个缺陷。这件事后来变成习惯：功能写完先跑真实路径，别信单元测试的绿。

这个习惯和后面的五个 bug 是同一件事的两面——单元测试只验证「代码按我写的逻辑跑」，不验证「我的逻辑是不是对的」。

二、一天重做 3568 道题

09-20 把全部 3568 道题从原始模型分片重建，逐题修复，校验器升到 spec v1.1。

为什么值得重做？因为第一版题源是「能出题」的水平，不是「能考人」的水平：干扰项经常是同一个词的不同词性，辨析卡写成「因为其他三个不对」。这种题做一百遍也学不到东西。

重做之后长出一整条工具链：出题提示词生成、分片合并、全量校验、截断痕迹扫描、逐题缺陷扫描（歧义 / 错位 / 模板 / 长度 / 万能项 / 同题重复）。

**内容质量不能靠抽查，只能靠把判据写成可执行的检查。**抽查能发现这一次的错，检查器能拦住下一批。

三、删除比写入难

09-25 做生词本云端同步，顺手补上了墓碑。

同步系统里最难的不是「写」，是「删」。只删本地记录，下次从另一台设备同步，那个词会原地复活。所以删除必须留一条标记，而标记本身也要按条 LWW 同步——两台设备各自删了同一个词，结果必须收敛，不能来回翻。

同一天还加固了多标签页会话守卫：两个标签页同时答题时，token 刷新和状态写入会互相踩。

这两件事的共同点是：**它们都只在「同时」发生时才错。**单设备、单标签页、单次操作，全部正常。

四、五个「看起来在工作」的 bug

10-27 做了一次全量审查，五个缺陷很有代表性：

  1. 报告页分模式正确率的分母只累加答错数，能显示 >100%。
  2. 题源校验器的「兼容版本集合」漏了当前版本 1.2，22 章题源全部误报不一致——噪声把真信号埋了。
  3. 注册接口的限流只查不记，blockedUntil 永远 0，等于可以无限枚举邮箱。
  4. 后台「近 7 天报错」拿 ISO 的 T 去比 sqlite datetime('now') 的空格，字典序里 " " < "T"，临界那天整天算错。
  5. 登录表单写了 novalidate: "false"——布尔属性存在即生效，原生校验全被关掉。

第 2、3、4 条是同一类：**代码看起来在工作，其实从来没生效。**这类 bug 不报错，只会让门禁变绿。第 5 条更狠一点：写了一个「关闭关闭」的值，语法上完全合法。

五、性能改到最后，问题变成「什么时候必须写」

重度用户存档 2600 词、376KB，点「下一题」主线程 p50 10.4ms，其中约 8ms 是两次 376KB 的 JSON.stringify——advance() 一次，renderWord() 末尾一次。

改动很小：saveLocal() 排队到微任务，同一任务内只写一次最终状态，切题就少了一半序列化。

但它立刻引出一个新问题：微任务能不能赶上关页？不能保证。于是必须另开同步出口 flushLocalSave()，在 beforeunload / pagehide / visibilitychange 三处现场落盘；applyUser() 改 userKey 之前也必须先 flush，否则排队中的写入会落进新账号的命名空间。

**任何「延后写入」的优化，都必须同时回答「什么时候不能再延后」。**这个问题答不上来，优化就是把丢数据的时间窗口从 0 扩大到一次任务。

代价与局限

墓碑方案假设本地时钟可信。 按条 LWW 收敛的前提是两台设备的时间大致可比；时钟被手动改过，收敛结果就会偏向「时间更晚」的那台。项目没有做逻辑时钟，这是已知简化。

性能数据只有一个样本。 p50 10.4ms 来自一台机器、一份 376KB 的存档。词量再大一倍会怎样，没有测——按线性推算并不可靠，因为 JSON.stringify 的开销与结构有关，不只是字节数。

「重写」这个决定没有对照。 第二天重写界面与同步模型是对的，但没法证明「在原结构上打补丁」一定更差。它只是一次基于直觉的判断，事后被结果支持。
